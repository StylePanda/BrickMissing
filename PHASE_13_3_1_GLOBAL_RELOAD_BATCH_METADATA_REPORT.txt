PHASE 13.3.1 – GLOBAL INVENTORY RELOAD + BATCH PURCHASE METADATA

1. Executive Summary
====================
Die Sets-Seite bietet nun einen klaren globalen „Alle Set-Inventare aktualisieren“-
Einstieg. Er verwendet den bestehenden Bulk-Sync: pro eigenem Set ein POST, strikt
sequenziell, mit derselben zentralen Rebrickable-Drosselung und Fehlerfortsetzung.

Der Mehrfach-Neukauf unterstützt Kaufdatum, Kaufpreis, Zustand und Notizen. Diese
Felder werden pro Set serverseitig whitelisted und validiert. Der Batch setzt nur in
diesem Workflow den bestehenden Aufbaustatuswert „gebaut“ (Anzeige „Aufgebaut“).
Nach erfolgreichem Inventory-Sync werden die benötigten Mengen als vorhanden
initialisiert.

2. Root Cause / bisherige UX-Lücke globaler Reload
==================================================
Vorher existierte nur der globale sequenzielle Sync mit der allgemeinen Bezeichnung
„Alle Sets synchronisieren“. Ein ausdrücklich als Inventar-Abgleich erkennbarer
Einstieg und eine erklärende UI fehlten. Der fachliche Sync selbst war bereits die
richtige zentrale Reconciliation-Logik.

3. Globale Reload-Architektur
=============================
Auf der Sets-Seite gibt es zusätzlich den Button „Alle Set-Inventare aktualisieren“.
Er öffnet den bestehenden Bestätigungsdialog und verarbeitet das vorhandene, aktive
Owner-Manifest. Jeder Set-Endpunkt validiert den Owner erneut.

4. Verwendeter Rebrickable-Sync
================================
Für jedes Set wird unverändert synchronize_set() aufgerufen. Damit werden Referenzen
upserted, neue Positionen angelegt, entfernte Positionen gemäß bestehender Semantik
auf Sollmenge 0 gesetzt und Fehlteile-Spiegel aktualisiert.

5. User-State-Schutz
====================
Der globale Reload übergibt bulk=1 und löst dadurch niemals den Session-Marker oder
initialize_newly_purchased_inventory() aus. owned_quantity, Part-Status, Notizen,
unassigned_found_quantity, Kaufdaten, build_status und condition bleiben erhalten.

6. Rate-Limit-/Sequenzlogik
===========================
set-bulk-sync.js verwendet weiterhin eine await-Schleife ohne Promise.all. Die zentrale
Rebrickable-HTTP-Schicht mit Request-Spacing, Retry-After, Backoff und begrenzten
Retries bleibt unverändert. Es entsteht kein langer Gesamtrequest. Der Limiter ist wie
zuvor process-lokal und nicht workerübergreifend global synchronisiert.

7. Globale Reload-UI
====================
Der neue Button nutzt die bestehende Progressbar, zeigt Set n von m, aktuelle
Setnummer/Name sowie erfolgreich und fehlgeschlagen. Fehlerhafte Sets erscheinen in
der Fehlerliste; bereits erfolgreich abgearbeitete Sets bleiben erhalten.

8. Batch-Kaufmetadaten
======================
Die Vorschauseite ergänzt globale Standardwerte für Kaufdatum, Zustand und Notizen.
Jede bereite Setzeile erhält eigene Eingabefelder für Kaufdatum, Preis, Zustand und
Notizen. Der Preis ist bewusst pro Set editierbar.

9. Tatsächlich vorhandene LegoSet-Kauffelder
============================================
Im Modell vorhanden und verwendet: purchase_date (DateField), purchase_price
(DecimalField), condition (Choice-Whitelist) und notes. Ein purchase_source-,
store- oder Händlerfeld existiert nicht; dafür wurde keine Migration und kein
Ersatzfeld erfunden.

10. Globale Defaults
====================
Die Batch-Maske stellt Default-Kaufdatum, Default-Zustand (Neu) und Default-Notizen
bereit. Sie werden beim Aufbau der Vorschauzeilen initial übernommen.

11. Pro-Set Overrides
=====================
Preis, Datum, Zustand und Notizen werden in jeder Vorschauzeile separat gehalten und
beim jeweiligen Import-Request übertragen. Eine spätere Änderung einer Zeile wird
nicht durch erneute Vorschau überschrieben.

12. Preisvalidierung
====================
Der Server akzeptiert Decimal-Werte, normalisiert österreichisches Komma zu Punkt,
verbietet negative Werte und mehr als zwei Nachkommastellen. Es wird kein Float
gespeichert.

13. Kaufdatumvalidierung
========================
Der Server verwendet date.fromisoformat(); leere Eingaben bleiben erlaubt, ungültige
Werte schlagen nur für den betroffenen Set-Request fehl.

14. Batch-Buildstatus
====================
Jeder neu über den Batch angelegte LegoSet-Datensatz erhält build_status="gebaut".
Das entspricht der bestehenden Anzeige „Aufgebaut“. Normales Set-Anlegen und der
einzelne Neu-gekauft-Workflow wurden nicht geändert.

15. Vollständigkeitslogik
=========================
Nach erfolgreichem Batch-Sync wird initialize_newly_purchased_inventory() ausgeführt.
Dadurch gilt required == owned für normale Positionen, Minifiguren und
MinifigureParts; die bestehende abgeleitete completeness ergibt „vollständig“.

16. Servervalidierung
=====================
Nur set_number, purchase_date, purchase_price, condition und notes werden explizit
übernommen. Setnummer, Datum, Decimal, Choice und Notizlänge werden serverseitig
geprüft; Clientwerte werden nicht blind auf das Model gemappt.

17. Atomicity
============
Der Einzelimport bleibt pro Set transaction.atomic. Bei Sync- oder Metadatenfehlern
wird kein halbfertiges neu angelegtes Set zurückgelassen; andere Browser-Requests des
Batch laufen weiter.

18. Fehlerbehandlung
====================
Die bestehende Frontend-Sequenz zählt Erfolg, Überspringen und Fehler. Ein ungültiger
Preis oder ein ungültiges Datum erzeugt einen Fehlerstatus für dieses Set, nicht für
den gesamten Stapel.

19. Security
============
Neue und bestehende Endpunkte bleiben login_required. Mutationen sind POST-only und
CSRF-geschützt. Es werden keine API-Keys oder Secrets an den Client übertragen.

20. Owner Isolation
===================
Manifest und Einzelendpunkt filtern nach owner=request.user und aktiven, nicht
gelöschten Sets. Bereits vorhandene Sets eines anderen Owners sind nicht sichtbar.

21. Performance
===============
Globaler Reload: ein Request pro Set. Batch: Metadatenvorschau getrennt vom
vollständigen Inventory-Sync, ein Import-Request pro Set, keine Parallelisierung und
keine zusätzlichen Requests für Kaufmetadaten.

28. Production-Testplan
=======================
GLOBAL RELOAD:
1. Ein Set mit absichtlich falscher Fehlmenge merken.
2. „Alle Set-Inventare aktualisieren“ starten und Progress beobachten.
3. Nach Abschluss Fehlmenge sowie owned/status/Notizen stichprobenartig prüfen.

BATCH:
4. Drei neue Sets eingeben, gemeinsames Kaufdatum setzen.
5. Für jedes Set einen unterschiedlichen Preis und ggf. Zustand/Notizen setzen.
6. Import ausführen, jedes Set öffnen und Kaufdaten prüfen.
7. Aufbaustatus „Aufgebaut“, Vollständigkeit „Vollständig“ und mehrere required==owned
   Positionen inklusive Minifiguren prüfen.
8. Späteren normalen Sync ausführen und User-State erneut kontrollieren.

29. Bekannte Einschränkungen
============================
Es gibt kein Kaufort-/Händlerfeld im aktuellen LegoSet-Modell; dieses bleibt eine
offene spätere Erweiterung. Der globale Reload zeigt erfolgreiche Syncs, aber keine
separate fachliche „unverändert“-Klassifikation, da der bestehende Sync keine
Änderungsanzahl zurückliefert. Der Rate-Limiter ist process-lokal.
