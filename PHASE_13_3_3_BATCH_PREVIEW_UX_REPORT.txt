PHASE 13.3.3 – BATCH PREVIEW PERFORMANCE + STATE FIX + PER-SET PURCHASE DATA

1. Root Cause langsame Preview
==============================
Die bisherige Sammel-Preview verarbeitete alle Nummern synchron in einem Request.
Zusätzlich nutzte sie den allgemeinen Metadaten-Service, der neben dem Set-Endpunkt
Theme-Endpunkte und eine Minifiguren-Zählabfrage ausführen konnte.

2. Vorherige API-Aufrufe
========================
Vorher waren je neuem Set bis zu vier Rebrickable-Requests möglich: Set-Metadaten,
bis zu zwei Theme-Details und eine Minifiguren-Seite. Parts und Minifiguren-Parts wurden
im Preview-Pfad nicht geladen, der synchrone Sammelrequest blockierte dennoch bis zum
letzten Set.

3. Neue Preview-Architektur
===========================
Die Browseroberfläche prüft die normalisierten Setnummern nun einzeln über
POST /sets/mehrere-neue/vorschau/einzel/. Nach jeder Antwort wird die Zeile sofort
gerendert. Der bestehende Sammel-Endpunkt bleibt kompatibel und verwendet ebenfalls
den leichten Preview-Service.

4. API-Aufrufe nachher
======================
Der neue rebrickable_set_preview()-Service führt pro Set genau einen zentral
gedrosselten Set-Metadaten-Request aus. Keine Parts-, Minifiguren- oder Theme-Requests
werden während der Preview ausgeführt. Vollständiger Sync bleibt dem Import vorbehalten.

5. Progress UI
==============
Während der Prüfung erscheint „Set n von m wird geprüft“, die Progressbar läuft mit
und bereits fertige Ergebnisse bleiben sichtbar.

6. Root Cause hängendes Prüfen
==============================
Der frühere Sammel-Submit hatte keinen zentralen Abschlusszustand für alle Fehler- und
Antwortpfade; die sichtbare Vorschau konnte erscheinen, während der Buttonzustand noch
auf laufend stand.

7. Loading-State-Fix
====================
Ein zentraler finally-Block setzt running, Button disabled/text und aria-busy sicher
zurück. Das gilt für Erfolg, Teilfehler und Exceptions. Während eines laufenden Laufs
verhindert running doppelte Preview-Starts.

8. Fehler-/Abort-Verhalten
==========================
Ein einzelnes ungültiges oder nicht gefundenes Set wird als eigene Fehlerzeile
angezeigt; die Schleife prüft die restlichen Nummern weiter. Die Import-Schleife bleibt
ebenfalls strikt sequenziell und fehlerfortsetzend.

9. Kaufdaten erst nach Preview
==============================
Die globalen Kaufdatenfelder wurden aus dem ersten Eingabeschritt entfernt. Schritt 1
enthält nur Setnummern und „Prüfen“. Erst bereite Vorschauzeilen erhalten editierbare
Kaufdaten.

10. Kaufdatum pro Set
=====================
Jede bereite Zeile erhält ein input type=date. Leere Werte bleiben erlaubt; der Server
validiert das ISO-Datum.

11. Kaufpreis pro Set
=====================
Jede bereite Zeile erhält ein Textfeld mit inputmode=decimal. Eingaben wie 169,99
werden serverseitig als Decimal mit zwei Nachkommastellen verarbeitet.

12. Zustand/Notizen
===================
Zustand (Neu/Gebraucht) und Notizen sind ebenfalls pro bereiter Zeile editierbar.
Nicht importierbare oder bereits vorhandene Sets erhalten keine unnötigen Eingabefelder.

13. Importpayload
=================
Der Einzelimport überträgt ausschließlich die Werte der jeweiligen Preview-Zeile:
set_number, purchase_date, purchase_price, condition und notes. Alte globale Hidden-
Werte werden nicht verwendet.

14. Servervalidierung
=====================
Die Whitelist bleibt serverautoritativ. Datum, Decimal-Preis, Zustand, Notizlänge und
Setnummer werden je Request validiert; ungültige Metadaten betreffen nur dieses Set.

15. Bestehender Buildstatus
===========================
Phase-13.3.1 bleibt unverändert: bestätigte Batch-Imports setzen build_status auf
„gebaut“ (Anzeige „Aufgebaut“). Normale und einzelne Neu-gekauft-Workflows ändern sich
nicht.

16. Vollständigkeit
===================
Nach erfolgreichem vollständigem Sync initialisiert der bestehende Service benötigte
Mengen als vorhanden; required == owned und die abgeleitete Vollständigkeit bleibt
„vollständig“.

17. Security
============
Preview-one und Import-one sind login_required, POST-only und CSRF-geschützt. Keine
API-Keys gelangen in HTML oder JavaScript.

18. Owner Isolation
===================
Bereits vorhandene Sets und alle Rebrickable-Ergebnisse werden ausschließlich im
Kontext request.user behandelt. Fremde Sets können nicht über Batch-IDs eingebunden
werden.

25. Production-Testplan
=======================
1. 3–10 Setnummern eingeben und nur „Prüfen“ starten.
2. Prüfen, dass erste Ergebnisse sofort erscheinen und Progress/„Prüfen“ sauber endet.
3. In der ersten Eingabestufe sicherstellen, dass keine Kaufdatum-/Preisfelder sichtbar

26. Bekannte Einschränkungen
============================
Die Browserprüfung ist bewusst seriell, um Rebrickable nicht aggressiv zu parallelisieren.
Die alte Sammel-Preview bleibt als kompatibler Backend-Endpunkt bestehen, der reguläre
UI-Pfad verwendet jedoch die sofort sichtbare Preview-one-Sequenz. Eine optionale
„Datum auf alle anwenden“-Komfortaktion wurde nicht ergänzt.
