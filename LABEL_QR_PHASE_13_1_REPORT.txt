1. AUSGANGSLAGE
================

Grundlage war der vollständig gelesene Bericht LABEL_QR_GENERATOR_AUDIT_REPORT.txt.
Die vorhandene Architektur besteht weiterhin bewusst aus zwei getrennten Systemen:

- dem festen Label Studio unter /organisation/etiketten-qr/ mit vier Layouts,
  Live Preview, lokaler SVG-QR-Erzeugung, PUBLIC_URL, Image Proxy und den festen
  HERMA-/Avery-Geometrien;
- dem generischen Legacy-System auf Basis vorhandener LabelTemplate-Datensätze.

Phase 13.1 hat diese Systeme nicht zusammengeführt und keine Benutzerdaten verändert.
Die bestätigten P0-Probleme wurden innerhalb der vorhandenen Architektur gehärtet.


2. B1 CONFIGURATION FIX
=======================

Neu ist die zentrale Laufzeit-Normalisierung in
apps/organizer/label_configuration.py.

Unterstützt und normalisiert werden:

- rows: positiver Integer, Bereich 1 bis 20, Default 4;
- columns: positiver Integer, Bereich 1 bis 10, Default 2;
- margin_top/right/bottom/left: endliche, nichtnegative Zahl, Bereich 0 bis 50 mm,
  Default 0;
- qr_code: definierte Boolean-Auswertung für Boolean, 0/1 und gebräuchliche
  true/false-Strings;
- text: sicherer String, None wird zum Leerstring;
- Nicht-Dictionary-Konfigurationen: vollständiger Rückfall auf sichere Defaults.

Ungültige Zahlen einschließlich nicht endlicher Werte, negative Werte und absurde
Werte können dadurch keinen HTTP 500 mehr auslösen. Gültige, physisch passende
Bestandskonfigurationen behalten ihre bisherige Semantik.


3. B2 START FIX
===============

Der generische Preview-Endpunkt verwendet jetzt normalize_start().

- ungültig, leer oder nicht numerisch -> 1;
- kleiner als 1 -> 1;
- größer als Kapazität -> Kapazität;
- es entsteht keine ValueError-/OverflowError-basierte HTTP-500-Antwort.

Das feste Studio besaß bereits eine defensive Behandlung seiner numerischen
Queryparameter. Diese wurde beibehalten.


4. INVENTORY QR FIX
===================

Der generische Inventory-QR enthält nicht mehr
inventory:<pk>:<part_number>.

Er enthält jetzt eine absolute BrickMissing-URL zur bereits vorhandenen Route:

  inventory:edit -> /inventar/<item-pk>/

Die Origin wird mit derselben _public_origin()-Logik wie beim Set-QR gebildet:
Production PUBLIC_URL hat Vorrang, andernfalls wird die Request-Origin verwendet.
Die Zielroute ist loginpflichtig und lädt das InventoryItem ausschließlich mit
owner=request.user. Es wurde kein neuer Resolver erfunden. Der QR enthält weder
Teilenummern als vertrauliche Nutzdaten noch Secrets oder Tokens. Ein nicht
angemeldetes Scan-Gerät wird weiterhin zur Anmeldung geleitet.


5. UNKNOWN COMPLETENESS
=======================

set_completeness() liefert bei required <= 0 nun:

  key=unknown, label=Unbekannt

Ein leeres, nicht synchronisiertes oder ausschließlich aus ignorierten Ersatzteilen
bestehendes Set wird somit nicht mehr als Vollständig ausgewiesen. Belastbare Daten
liefern unverändert complete/Vollständig oder incomplete/Unvollständig.

Die vorhandenen Aufrufer wurden geprüft:

- Setdetail unterstützt unknown bereits und unterdrückt dort die irreführende
  Mengenangabe;
- Set-Labels zeigen das neue Label Unbekannt;
- AJAX-Minifiguren-/Setstatus erhält weiterhin dieselbe Dictionary-Struktur;
- stored_completeness_value() bildet unknown kompatibel auf den bereits im
  LegoSet-Feld gebräuchlichen Wert unbekannt ab;
- der Reconcile-Management-Command bleibt damit semantisch korrekt.

umgeschrieben und keine künstliche Integration in das feste Studio gebaut. Eine
ownerweite exklusive Standardauswahl und Studio-Integration gehören zu Phase 13.2.

9. QR QUIET ZONE
================

qr_svg() akzeptiert nun einen optionalen Keyword-Parameter border.

- kompatibler Default für TOTP und andere bestehende Aufrufer: border=2;
- gedruckte Studio- und Legacy-Label-QRs: border=4 Module.

Die QR-Erzeugung bleibt vollständig lokal über qrcode und SvgPathImage. Es wurde
keine externe QR-Abhängigkeit eingeführt. Tests sichern sowohl den TOTP-Default als
auch die scanfreundliche Label-Konfiguration.

============================

12. PRINT READINESS
===================

Der Studio-Druckbutton besitzt eine label-spezifische Vorbereitung:

- eine noch laufende Preview-Aktualisierung wird kurz abgewartet;
- noch ladende Bilder im aktiven Labelbereich werden über load/error beobachtet;
- bereits geladene oder fehlgeschlagene Bilder blockieren nicht;
- Preview- und Bildwartephase haben jeweils einen begrenzten 3-Sekunden-Fallback;
- währenddessen zeigt der Button Druck wird vorbereitet …;
- danach wird window.print() aufgerufen.

Die globale data-print-page-Logik überspringt nur den neuen data-label-print-Button.
Alle anderen bisherigen Druckbuttons verwenden unverändert die globale Sofortfunktion.

keine Etiketten erzeugen kann, wird dies separat verständlich erklärt.
