BrickMissing 8.5.3 – Status-Speichern/JSON-Hotfix
IMPLEMENTATION STATUS: READY
PRODUCTION VALIDATION: PENDING
Version vorher: 8.5.2
Version nachher: 8.5.3

1. Reproduktion: Eine lokale, transaktional zurückgerollte Set-Zuordnung mit required=2, owned=0, missing=2 und sichtbarem Status „Fehlt“ wurde per Statusformular auf „Erhalten“ (received) gestellt und gespeichert.
2. Endpoint: /fehlteile/<UUID>/status/; URL-Name catalog:missing_part_status, Django-View apps.catalog.views.missing_part_status.
3. Request: POST, FormData mit status=received und CSRF-Token; Accept: application/json und X-Requested-With: XMLHttpRequest.
4. HTTP-Status vor Fix: 400 Bad Request.
5. Content-Type vor Fix: text/html; charset=utf-8.
6. Response vor Fix: Plaintext im HttpResponse, keine JSON-Struktur.
7. Fachliche Meldung: „Ein Besitzstatus ist erst ohne offene Fehlmenge zulässig.“
8. Root Cause: workflow_status_is_consistent lehnte den Besitzstatus bei offener Fehlmenge fachlich korrekt ab. Die View gab vor der JSON-Erfolgsverzweigung einen Plaintext-HttpResponse zurück, obwohl der Fetch-Handler unabhängig vom HTTP-Status response.json() aufrief. Der resultierende SyntaxError wurde als technische Meldung im UI angezeigt. Zusätzlich startete die globale Formularlogik in app.js einen Spinner, den der bisherige Status-Handler nicht entfernte.
9. Backend-Fix: Der Status-Endpunkt gibt bei erwartbaren Validierungsfehlern und owner-scoped 404 für XMLHttpRequest JsonResponse mit {ok:false,message:...} aus. Nicht-AJAX-Formulare behalten den bestehenden Plaintext-400-Vertrag. Die Statusvalidierung, autoritative Mengenabfrage und der Erfolgsweg bleiben erhalten.
10. Frontend-Fix: missing-parts.js prüft Content-Type und response.ok, parst JSON nur bei passendem Typ, übernimmt die vorhandene fachliche message und verwendet für defektes JSON, HTML oder Netzwerkfehler eine neutrale Meldung. Die globale Ladezustandslogik überspringt ausschließlich .status-form; deren AJAX-Handler verwaltet Spinner und Button selbst.
11. Vertrag nach Fix: Erfolg HTTP 200, application/json, {ok:true,part:{...}}. Fachliche Ablehnung HTTP 400, application/json, {ok:false,message:"Ein Besitzstatus ist erst ohne offene Fehlmenge zulässig."}. Ungültiger Status ebenfalls HTTP 400 JSON; fremder/nicht vorhandener Datensatz HTTP 404 JSON. Derselbe transaktionale Reproduktionsrequest wurde nach dem Fix erneut ausgeführt und bestätigte genau HTTP 400/application-json, ohne gespeicherte Status- oder Mengenänderung.
12. Validierungsfehler: Die Speicherung wird weiterhin abgelehnt; Status bleibt missing, quantity=2, owned=0, missing=2. Das UI zeigt die Fachmeldung statt „Unexpected token“ und stellt das Dropdown auf den angezeigten Status zurück.
13. Gültiger Wechsel: Mit gleicher Fehlmenge ist „Bestellt“ (ordered) erlaubt; HTTP 200 JSON, sichtbarer Zuordnungsstatus „Bestellt“, Menge unverändert. Der Gruppenstatus bleibt mengenbasiert.
14. Ladezustand: Der Handler setzt is-loading, aria-busy und disabled während des Requests und entfernt alle in finally bei Erfolg, Validierungsfehler, HTML, defektem JSON und Netzwerkfehler. Ein 15-s-Abbruch verhindert unbegrenztes Warten.
15. UI nach Fehler: Zuordnungsbadge, Dropdown, Gruppenbadge, owned/missing und Progress bleiben unverändert; alte Fehlermeldungen werden nach erfolgreichem Speichern entfernt.
16. Owner-Isolation: Query bleibt owner- und deleted_at-gefiltert. Fremde und nicht vorhandene IDs ergeben denselben JSON-404 ohne Mutation. Kein neuer Berechtigungsweg.
