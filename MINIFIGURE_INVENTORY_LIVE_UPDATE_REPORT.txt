BRICKMISSING 8 – MINIFIGUREN-BESTAND / LIVE-STATUS – ABSCHLUSSBERICHT

1. ROOT CAUSE

Die Datenbankänderung war bereits persistent, die Frontend-Aktualisierung jedoch nur
auf das lokale Formular, seine Tabellenzeile und einen DOM-nahen Figurencontainer
begrenzt. Auf Seiten mit mehreren Darstellungen desselben Minifigurenteils blieben
weitere Zeilen, Mengen, Status-Badges und Figurenfortschritte veraltet. Einige
Templates besitzen außerdem nicht alle vom JavaScript erwarteten data-Attribute.

2. BETROFFENE DATEIEN

- apps/organizer/views.py
- static/js/minifigure-inventory.js
- apps/organizer/tests.py

3. GEÄNDERTE DATEIEN

- apps/organizer/views.py
- static/js/minifigure-inventory.js
- apps/organizer/tests.py
- MINIFIGURE_INVENTORY_LIVE_UPDATE_REPORT.txt

4. ALTER DATENFLUSS

Aktion -> POST -> MinifigurePart.owned_quantity speichern -> JSON berechnen -> nur
lokale DOM-Zeile bzw. lokal gefundene Figurenanzeige aktualisieren.

5. NEUER DATENFLUSS

Aktion -> POST -> Transaktion und Zeilensperre -> MinifigurePart.owned_quantity
speichern -> Datensatz erneut aus DB lesen -> Figur und Set aus DB neu laden ->
vollständigen Zustand mit IDs zurückgeben -> alle Formulare/Zeilen zur identischen
Bestands-URL und alle zugehörigen Figurenanzeigen aktualisieren.

6. DATENBANKVERHALTEN VOR DEM FIX

MinifigurePart.owned_quantity wurde durch save(update_fields=["owned_quantity"])
bereits persistent gespeichert. Die richtige Zeile wurde durch Kombination aus
owner-geschützter SetMinifigure und zugehörigem MinifigurePart ermittelt. Die
sichtbare Oberfläche konnte dennoch einen älteren Zustand zeigen.

7. DATENBANKVERHALTEN NACH DEM FIX

Die bestehende atomare Speicherung und select_for_update()-Sperre bleiben erhalten.
Nach save() wird MinifigurePart explizit mit refresh_from_db() erneut gelesen.
Figuren- und Setstatus werden anschließend aus frisch geladenen Relationen berechnet.
Keine Produktionsdaten, Migrationen oder Schemaobjekte wurden verändert.

8. STATUSBERECHNUNG VOR DEM FIX

Die serverseitige Berechnung war fachlich korrekt (fehlend, teilweise, komplett),
erreichte aber nicht zuverlässig alle sichtbaren DOM-Repräsentationen.

9. STATUSBERECHNUNG NACH DEM FIX

Die Serverberechnung bleibt die einzige maßgebliche Statusquelle. Die JSON-Response
enthält Teil-ID, Figuren-ID, benötigt, vorhanden, fehlend, Teilstatus sowie Figuren-ID,
vorhanden, benötigt, fehlend, Prozentwert und Gesamtstatus. JavaScript errät keine
Mengen oder Statuswerte.

10. FRONTEND-AKTUALISIERUNG

Alle Formulare mit derselben, IDs enthaltenden Bestands-URL werden zusammengeführt.
Aktualisiert werden Number-Inputs, vorhandene/fehlende Mengenmarker, Teilstatus,
Figurenfortschritt, Figurenstatus und Set-Vollständigkeit. Versteckte Werte der
✓-/×-Aktionen werden nicht überschrieben. Doppeltes Absenden während eines laufenden
Requests bleibt gesperrt; Fehler stellen den vorherigen Eingabewert wieder her.

11. VERHALTEN DES X-BUTTONS

Der X-Button sendet owned_quantity=0 an denselben geschützten POST-Endpunkt. Der Wert
wird persistent gespeichert. Response und DOM wechseln unmittelbar auf fehlend bzw.
unvollständig; eine vollständige Seite wird nicht neu geladen und kein Fenster geöffnet.

12. VERHALTEN BEI MANUELLER MENGENÄNDERUNG

Speichern sendet die eingegebene Menge an denselben Endpunkt. Nach erfolgreicher
Persistenz liefert der Server den neu berechneten Teil-, Figuren- und Setzustand.
Alle parallelen Darstellungen werden auf diesen Zustand synchronisiert.

13. NEU HINZUGEFÜGTE TESTS

- Response-IDs und vollständige Mengenwerte
- manuelle Übergänge 0 -> 1, 1 -> 0 und Teilstatus bei benötigter Menge 2
- teilweise/vollständig/fehlend auf Teil- und Figurenebene
- X-Button-Semantik vollständig -> unvollständig
- Persistenz durch refresh_from_db()
- wiederholter Request / Idempotenz
- Schutz vor Änderung eines Teils aus einer anderen Figur
- vorhandene Fremdbenutzer-Schutztests bleiben bestehen

14. TESTERGEBNISSE

- Gezielte Organizer-Tests: 8/8 bestanden
- Vollständige Django-Testsuite: 203/203 bestanden
- python manage.py check: keine Probleme
- Ruff: alle Prüfungen bestanden
- makemigrations --check --dry-run: keine Änderungen erkannt
- node --check static/js/minifigure-inventory.js: bestanden

15. VERBLEIBENDE BEKANNTE PROBLEME

Keine im geprüften Minifiguren-Bestandsfluss bekannt.

16. RISIKEN / SEITENEFFEKTE

Gering. Der Fix verändert kein Schema und keine Berechnungsregeln. Auf Seiten mit sehr
vielen doppelten Darstellungen wird nach einer Änderung eine kleine DOM-Suche über die
Bestandsformulare ausgeführt. Die Datenbank bleibt maßgebliche Quelle.

17. VERHALTEN NACH BROWSER-RELOAD

Bestätigt durch Persistenztests: Nach erneutem Datenbankabruf steht derselbe
owned_quantity-Wert zur Verfügung, aus dem dieselben Teil-, Figuren- und Setstatuswerte
berechnet werden. Ein Browser-Reload zeigt daher denselben Zustand wie die Live-Ansicht.

DEPLOYMENT

Kein Deployment und keine Produktionsdatenänderung durchgeführt. Keine Migration nötig.
Da static/js/minifigure-inventory.js geändert wurde, ist beim später freigegebenen
Deployment collectstatic erforderlich; danach ist der bestehende Django-Service gemäß
dem vorhandenen Deployment-Ablauf neu zu starten.
