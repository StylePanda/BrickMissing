PHASE 13.3 – SET BATCH IMPORT + INVENTORY RECONCILIATION

1. Executive Summary
====================
Die bestehende Rebrickable-Synchronisation wurde für den Neu-gekauft-Workflow
wiederverwendet. Nach einem erfolgreichen, vollständigen Sync werden ausschließlich
die Anforderungen dieses neu markierten Sets als vorhanden initialisiert. Normale
Synchronisationen verändern User-Mengen nicht.

Zusätzlich gleicht jeder erfolgreiche Sync die Rebrickable-Referenzanforderungen mit
dem lokalen Setinventar ab. Bestehende Zeilen bleiben erhalten; nicht mehr gelieferte
Referenzen werden auf Sollmenge 0 gesetzt. Eine vorhandene Fehlteile-Spiegelzeile wird
auf die neue Sollmenge angepasst, während owned, Status und Notizen soweit möglich
erhalten bleiben.

Für mehrere neue Sets gibt es eine zweistufige, owner-geschützte Oberfläche:
Eingabe/Vorschau und danach ein einzelner POST pro Set. Die Browser-Sequenz ist strikt
seriell und erzeugt keine minutenlange Gesamtanfrage.

2. Bestehender Set-Import-Flow
==============================
Die normale Route /sets/neu/ verwendet weiterhin LegoSetForm und die bestehende
Set-Anlage. Das Rebrickable-Lookup lädt Metadaten. Der Sync-Endpunkt
/integrationen/rebrickable/sets/<id>/ bleibt zentraler Sync-Einstieg.

3. Neu-gekauft-Initialisierung
==============================
Der Neu-gekauft-Preset setzt weiterhin nur condition=neu. Beim Speichern wird ein
Session-Marker für genau dieses Set gesetzt. Erst nach erfolgreichem
Rebrickable-Sync ruft der Sync-Endpunkt initialize_newly_purchased_inventory() auf.
SetInventoryItem.owned_quantity wird auf required_quantity gesetzt; bei
SetMinifigure und MinifigurePart wird owned_quantity auf quantity gesetzt.

4. Normale vs. neu-gekaufte Semantik
====================================
Ohne Session-Marker erfolgt keine Initialisierung. Spätere normale Syncs bewahren
owned_quantity und alle vorhandenen Workflowwerte. Ein fehlgeschlagener Sync erreicht
die Initialisierung nicht.

5. Minifiguren-/Part-Initialisierung
=====================================
Normale SetInventoryItems, SetMinifigures und MinifigureParts werden getrennt anhand
ihres jeweils vorhandenen Mengenmodells behandelt. Ersatzteile bleiben Referenzdaten;
die Vollständigkeitsberechnung schließt sie weiterhin aus.

6. Root Cause falscher Fehlmengen
=================================
Der bisherige Sync aktualisierte vorhandene Rebrickable-Referenzzeilen, markierte
entfernte Positionen aber nicht und aktualisierte optionale Part-Spiegel nicht. Dadurch
konnte die Fehlteile-Anzeige historische Sollmengen weiterführen.

7. Rebrickable Reload/Reconciliation
====================================
Der vorhandene POST-Sync ist zugleich der sichere Set-Inventar-Reload. Es wurde keine
zweite HTTP-/Retry-Implementierung eingeführt. Neue Referenzen werden kanonisch
upserted; bekannte Identitäten werden wiederverwendet. Entfernte SetInventoryItems
und MinifigureParts werden nicht gelöscht, sondern mit Sollmenge/quantity 0 erhalten.

8. User-State-Erhaltung
=======================
owned_quantity, Minifigure-Notizen sowie Part-Status, Notizen und unassigned_found_quantity
werden nicht blind überschrieben. Bei einer reduzierten Anforderung wird vorhandenes
owned nur zur Einhaltung der Mengeninvariante auf höchstens die neue Sollmenge begrenzt.

9. Entfernte/neue Referenzpositionen
====================================
Neue Positionen werden angelegt. Entfernte Setpositionen bleiben historisch vorhanden
und sind durch Sollmenge 0 nicht mehr offen. Ein vorhandener Part-Spiegel wird so
angepasst, dass keine alte Fehlmenge weiter angezeigt wird.

10. Mengen-Reconciliation
=========================
Die SetInventoryItem-Fehlmenge bleibt required_quantity minus owned_quantity. Der
Fehlteile-Spiegel erhält die neue Sollmenge und behält seine vorhandene owned-Menge
(begrenzt durch die neue Sollmenge). Dadurch wird z.B. 3/1 nach einem Rebrickable-
Reload auf 2/1 und damit Fehlmenge 1 reduziert.

11. Fehlteile-End-to-End
=======================
Die Setinventarquelle und die optionale Part-Darstellung werden gemeinsam aktualisiert.
Die bestehende MinifigurePart-Reconciliation bleibt im selben Sync. Die vorhandene
Missing-Parts-Reconciliation und Cross-Source-Anzeige bleiben unverändert.

12. Batch-Import-Architektur
============================
Neue Routen:
- GET  /sets/mehrere-neue/
- POST /sets/mehrere-neue/vorschau/
- POST /sets/mehrere-neue/importieren/

Die Vorschau ist rein ownerbezogen und lädt nur Metadaten. Der bestätigte Import legt
pro Request genau ein Set an, synchronisiert es zentral und initialisiert es danach als
neu gekauft. Pro Set besteht eine eigene atomare Verarbeitung; ein Fehler löscht nur
das gerade neu erzeugte, fehlgeschlagene Set und stoppt den Browserablauf nicht.

13. Batch Parser
================
Zeilen, Komma, Semikolon und Whitespace werden akzeptiert. Rein numerische Setnummern
werden über normalize_rebrickable_set_number() mit -1 ergänzt. Doppelte Eingaben werden
entfernt und gezählt; ungültige Eingaben werden separat gemeldet.

14. Preview
===========
Die Vorschau kennzeichnet Bereit, Bereits vorhanden, Nicht gefunden/Fehler und zeigt
Name sowie Rebrickable-Metadaten, sofern verfügbar. Nur bereite Einträge sind zunächst
ausgewählt und können einzeln abgewählt werden.

15. Sequentieller Import
========================
set-batch-import.js verwendet eine await-Schleife. Es gibt kein Promise.all und pro Set
eine kurze HTTP-Anfrage. Fortschrittsbalken und aktuelles Set werden aktualisiert.

16. Rate-Limit-Verhalten
========================
Batch und Einzel-Sync verwenden ausschließlich die vorhandene zentrale
Rebrickable-HTTP-Schicht mit konservativem Request-Abstand, Retry-After und begrenztem
Backoff. Kein eigener Batch-Request und keine parallelen Rebrickable-Aufrufe wurden
eingeführt. Der Limiter bleibt wie zuvor process-lokal; mehrere Gunicorn-Worker sind
nicht global synchronisiert.

17. Progress UI
===============
Während des Imports wird „Set n von m“ inklusive Setnummer angezeigt. Nach Abschluss
werden erfolgreich, übersprungen und fehlgeschlagen gezählt.

18. Fehlerbehandlung
====================
Ein einzelner ValueError/Rebrickable-Fehler liefert einen Fehlerstatus für dieses Set.
Die Frontend-Schleife setzt danach mit dem nächsten Set fort.

19. Idempotenz
==============
Die bestehende active_set_number-Eindeutigkeit wird respektiert. Bereits vorhandene
Sets werden in Vorschau und Einzelimport übersprungen; ein wiederholter Batch erzeugt
keine zweite aktive LegoSet-Zeile. Das aktuelle Modell unterstützt keine parallelen
physischen Exemplare desselben aktiven Settyps über diese Route.

20. Security
============
Alle neuen Routen benötigen Login. Mutationen sind POST-only und verwenden Django-
CSRF. Rebrickable-Schlüssel werden weder in HTML/JS noch in Logs ausgegeben.

21. Owner Isolation
===================
Bestehende Sets werden ausschließlich mit owner=request.user geprüft. Batch-Vorschau,
Import und der vorhandene Sync greifen nicht auf fremde Setdaten zu.

22. Performance
===============
Vorschau ist Metadaten-orientiert; vollständige Teile-/Minifigurenabfragen erfolgen
erst beim bestätigten Import. Jeder Batch-Import verarbeitet ein Set pro Request,
vermeidet N+1 im neuen Browserablauf und nutzt die zentrale Rate-Limit-Schicht.

29. Production-Testplan
=======================
1. Ein neu gekauftes Set anlegen, synchronisieren und mehrere Teile prüfen:
   required == owned; Minifigur und MinifigureParts prüfen.
2. Ein Teil manuell als fehlend setzen, normalen Sync ausführen und prüfen, dass es
   weiterhin fehlt.
3. Ein Set mit bekannter falscher Menge auswählen, den vorhandenen Rebrickable-Sync
   als „Set-Inventar neu laden“ ausführen und required/owned/missing vergleichen.
4. Batch mit 3 Sets, danach 10 Sets, jeweils Fortschritt und Abschlusszahlen prüfen.
5. Bereits vorhandenes und absichtlich ungültiges Set testen; Restlauf und Owner prüfen.
6. Stichprobe der erfolgreich importierten Inventare und Print-/Label-Flows prüfen.

30. Bekannte Einschränkungen
============================
Der Limiter ist process-lokal wie in der bestehenden produktiven Architektur. Die
Vorschau nutzt den vorhandenen Metadaten-Service, der neben Setdaten ggf. kleine
Referenzabfragen ausführt. Es gibt keine globale automatische Produktionsbereinigung;
Reload bleibt bewusst benutzerinitiiert pro Set. Eine separate, benannte Reload-Route
wurde nicht geschaffen, weil der vorhandene zentrale Sync fachlich bereits diesen
Abgleich ausführt.

31. Verbleibende Aufgaben
=========================
Finale physische Produktionsprüfung, ggf. UX-Feinschliff der Batch-Vorschau und eine
spätere globale Reconciliation-Option bleiben außerhalb dieses begrenzten Workflows.
