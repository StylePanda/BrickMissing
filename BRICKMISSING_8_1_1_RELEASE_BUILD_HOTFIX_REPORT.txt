ROOT CAUSE
Beim Python-Import `from config.version import APP_VERSION` wird zuerst
`config/__init__.py` ausgeführt. Dieses initialisiert PyMySQL. Der bewusst mit
nacktem System-Python gestartete Release-Builder besitzt keine Django-/DB-
Runtime-Abhängigkeiten und brach deshalb vor dem Build mit
`ModuleNotFoundError: No module named 'pymysql'` ab.

TECHNISCHE LÖSUNG
- Die einzige fachliche Versionsquelle wurde aus dem nebenwirkungsbehafteten
  Package `config` in das neutrale Top-Level-Modul `brickmissing_version.py`
  verschoben.
- `brickmissing_version.py` enthält ausschließlich dependency-freie
  Versionskonstanten und setzt APP_VERSION auf 8.1.1.
- Django-Settings, Anwendungspaket, Kompatibilitätsmodul, Release-Builder,
  Release-Verifier, Smoke-Test und Tests lesen dieselbe zentrale Quelle.
- `pyproject.toml` verwendet weiter dynamische Paketversionierung und verweist
  jetzt auf `brickmissing_version.APP_VERSION`.
- Release-Build- und Verify-Allowlisten enthalten das zentrale Versionsmodul.
- Die drei direkt ausführbaren Release-Tools unterdrücken eigene Bytecode-
  Artefakte, damit ein aus dem Release gestarteter Verifier kein undeclariertes
  `__pycache__` im strikt geprüften Artefakt erzeugt.
- Keine neue Dependency, keine Migration, keine Produktionskonfiguration und
  kein zweiter manuell zu synchronisierender Versionswert.
